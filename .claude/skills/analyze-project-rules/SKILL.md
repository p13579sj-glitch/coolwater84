# 프로젝트 내부 룰 분석

주어진 프로젝트 루트 경로의 코드베이스를 읽기 전용으로 분석하여 `RULES.md`를 생성하거나 갱신한다. 이 문서는 이후 main agent가 개발 시 벗어나면 안 되는 컨벤션의 기준이 된다.

## 절차

1. 프로젝트 루트 구조(디렉터리, 주요 모듈/레이어)를 파악한다.
2. 다음 관점에서 반복되는 패턴을 찾는다:
   - 네이밍 규칙 (클래스/메서드/변수/파일)
   - 다중 값 반환 처리 방식 (예: tuple 대신 전용 클래스 사용 여부)
   - 예외/오류 처리 패턴
   - 의존성 주입·계층 구조 관례
   - 널 처리(nullable) 관례
   - 테스트 코드 배치·명명 관례
   - 그 외 반복적으로 나타나는 팀 고유 관습
3. 각 규칙은 실제 근거가 되는 코드 위치(`파일:라인`)를 최소 1개 이상 함께 기록한다. 근거 없는 추측성 규칙은 작성하지 않는다.
4. 기존 `RULES.md`가 있으면 덮어쓰지 않고 변경/추가된 부분만 갱신하며, 갱신 일자를 문서 상단에 남긴다.

## 출력 형식 (`RULES.md`)

```markdown
# 프로젝트 내부 룰 - <프로젝트명>

_최종 갱신: YYYY-MM-DD_

## <카테고리>

### 규칙: <한 줄 요약>
- 설명: ...
- 근거: `path/to/file.cs:42`, `path/to/other.cs:10`
```

## 하지 않는 것

- 코드 수정, 리팩터링, 새 파일 생성(RULES.md 제외) 금지
- `dotnet` 등 빌드/실행 명령 실행 금지
- 패키지 설치/업데이트 금지
- 근거 코드 없이 일반론적인 "모범 사례"를 룰로 기재하지 않음
